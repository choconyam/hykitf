# 관리 기준 안내 (SPC 규칙·알람 기준을 정할 때)

> 메인이 관리 기준이나 알람 규칙을 만들기 전에 끝까지 읽는다. AGENTS.md가 우선한다. [원인 분석 안내](causes.md)의 '정상 기준(기준선)' 줄과 '진짜 이상' 줄도 먼저 읽고 따른다.
> CAUSES.md에 적는 일은 메인이 결과 파일 경로와 명령을 문서 담당에게 넘겨 맡긴다. 문서 담당이 없을 때만 메인이 직접 쓴다.

- 규격 한계(제품이 지켜야 하는 값, 과제나 담당자가 정함)와 관리 한계(공정이 평소 움직이는 범위, 자료로 계산)를 구분해 적는다. 한쪽을 다른 쪽 대신 쓰지 않는다.
- 무엇을 한 점으로 볼지(웨이퍼·로트 측정값, 스텝 요약값)와 관리도를 어떻게 나눌지(장비·챔버·레시피·제품)를 먼저 정한다. 평소 수준이 다른 묶음을 한 관리도에 섞지 않는다.
- 관리 한계는 안정된 기준 기간의 자료로만 계산하고 그 뒤 기간으로 확인한다. 기준 기간에서 점검·부품 교체·세정 직후의 회복 구간, 이미 이상이 의심되는 장비·기간, 원인을 확인한 이상 점은 한계 계산에서만 뺀다(그 점에 표시 열을 붙인 사본을 만들어 --baseline-exclude 표시열=1). 뺀 점과 이유를 적는다.
- 계산은 `python3 trace_tools.py spc`로 한다(중심선, 관리 한계, 규칙 1~5와 EWMA 신호, 규격을 주면 Cpk). 묶음별 한계와 신호 수는 결과 옆 .md에 나온다. 웨이퍼·로트 식별 열은 --keep으로 남겨 측정 결과나 다른 관리도와 맞춰 본다. 관리도 그림은 plot으로 값·한계를 함께 그린다.
- 한계 폭을 3시그마로 고정하지 않는다. --k를 3~6으로 바꿔 가며 비교한다. 좁으면 빨리 잡지만 오경보가 늘고, 넓으면 반대다. 관리도 수(센서×스텝×장비)가 많을수록 우연한 신호도 그만큼 늘어나므로 더 넓게 잡거나 확인 조건을 붙인다.
- 후보를 적어도 셋 만든다: 한계 밖 한 점(--rules 1), 확인 조건을 붙인 것(연속 N점은 --confirm, 여러 센서나 스텝이 같은 웨이퍼에서 함께 벗어나는 조건은 관리도별 결과를 식별 열로 묶어 analysis/에서 계산), 거기에 EWMA 조기 경고를 더한 것(--ewma).
- 규칙을 더하면 오경보도 는다. 후보와 한계 폭마다 확인 기간에서 오경보(정상인데 신호), 놓침(알려진 이상인데 신호 없음), 이상을 잡기까지 걸린 점 수를 표로 비교한다. 기준 기간의 신호 수는 한계를 그 점들로 맞춰 작게 나오므로 참고만 한다. 표는 CAUSES.md 5절이나 과제가 정한 문서에 둔다.
- 기준을 바꿔서 살리는 양품(불량·알람으로 판정됐지만 실제 결과는 정상)과 새로 놓치는 불량을 같은 표에 건수로 적고, 가능하면 비용(폐기·재작업·장비 정지·불량 유출)으로 바꿔 비교한다. 어느 쪽을 우선할지는 담당자 답이나 사람이 정한 가정을 따르고, 조건이 같으면 더 단순한 규칙을 고른다.
- 값이 한쪽으로 치우치거나 앞뒤 점이 서로 닮았으면(.md의 치우침·앞뒤 닮음) 3시그마 한계의 오경보율이 달라진다. 그때는 백분위수 한계나 요약 단위 변경을 analysis/ 코드로 비교하고 한계를 적는다.
- 신호는 두 단계로 나눈다. 경고는 사람이 확인하는 단계로 좁은 한계나 EWMA처럼 빨리 잡는 규칙을 쓰고, 정지는 장비를 세우거나 로트를 보류하는 단계로 넓은 한계(--stop-k)나 확인 조건을 만족한 신호만 쓴다. 정지는 오경보 한 번의 손해가 크므로 확인 기간의 오경보가 0에 가까운지 따로 보인다.
- 단계마다 신호가 났을 때 할 일과 볼 사람, 한계를 다시 계산할 때(점검·부품 교체 뒤, 레시피 변경 뒤)를 적는다. 자료로 정할 수 없으면 질문 후보나 가정으로 둔다.
